      28| ## 1. Architecture Overview
      29| 
      30| ### 1.1 Core agent loop
      31| Claude Code is a **terminal-native agentic coding tool** built around a single core **agent loop** (a.k.a. the "agentic harness"):
      32| 
      33| ```
      34| user prompt
      35|    → build context (system prompt + CLAUDE.md + tools + conversation)
      36|    → LLM call (Anthropic Messages API, streaming)
      37|    → parse assistant response (text + tool_use blocks)
      38|    → for each tool_use: permission check → execute tool → append tool_result
      39|    → loop until model emits a final text turn with no pending tool_use
      40|    → render to TTY (streaming)
      41| ```
      42| 
      43| Key characteristics:
      44| - **Tool-use driven**: the model emits structured `tool_use` blocks; the client executes them locally and feeds `tool_result` back. The loop is a standard *ReAct*-style plan→act→observe cycle, but with rich local tooling and a permission gate on every mutating action.
      45| - **Streaming-first**: responses stream token-by-token to the terminal; tool calls are surfaced as they arrive.
      46| - **Stateless per-call, stateful session**: the model itself is stateless; session state (conversation, todos, file edits, checkpoints) lives client-side and is persisted to `~/.claude/projects/<project>/` and `file-history/`.
      47| - **Sub-loop / subagent isolation**: the `Task` tool (and agent teams) spawn child agent loops that run in their own context window and return a single summarized result to the parent (see §4).
      48| 
      49| ### 1.2 LLM provider usage
      50| - **Primary provider**: Anthropic **Messages API** (`api.anthropic.com`), via Claude models. Model tiers map to the roles `main` / `sonnet` / `opus` / `haiku` (fast/cheap model used for background classification, summarization, compaction, and the small-model "haiku" path; larger `sonnet`/`opus` for the main reasoning path).
      51| - **Model selection**: interactive `/model` picker; default per plan. Changelog shows `/model` changing the current session vs. default (`d` to set default). A `CLAUDE_CODE_SUBAGENT_MODEL` env var lets subagents use a different (often cheaper) model.
      52| - **Provider abstraction** (verified locally): `providers.json` supports `apiFormat: anthropic` and `runtimeKind: anthropic_compatible`, and the env-var surface (`ANTHROPIC_BASE_URL`, `ANTHROPIC_API_KEY`, `ANTHROPIC_MODEL`, `ANTHROPIC_DEFAULT_{HAIKU,SONNET,OPUS}_MODEL`) means **any Anthropic-compatible endpoint** can be used — including Ollama / self-hosted / LiteLLM-style gateways. The local instance points `ANTHROPIC_BASE_URL` at `http://ai:11434` (Ollama) with `gemma4`/`qwen3.6` models.
      53| - **Cloud providers** (changelog `[memory]`-corroborated): Bedrock, Vertex, and "Foundry" (Azure) are supported and propagate API-provider env vars to spawned processes (agent teams / tmux).
      54| - **1M context** variants exist (changelog: `1M` appears across many versions, e.g. `sonnet1m45MigrationComplete`, `opus1mMergeNoticeSeenCount` in local config) — long-context model variants are first-class.
      55| 
      56| ### 1.3 System prompt construction **[memory/inferred]**
      57| The effective system prompt is assembled at session start from layered sources:
      58| 1. **Base system prompt** — Anthropic-maintained harness prompt describing the agent loop, tool usage, output conventions, safety/permissions behavior, and "Claude Code" persona.
      59| 2. **Output style** (if set) — overrides tone/format instructions (see §5.4).
      60| 3. **CLAUDE.md memory hierarchy** (see §3.3) — injected as project/personal/enterprise instructions.
      61| 4. **Tool definitions** — the JSON schemas for the active tool set (Bash, Read, Write, Edit, Grep, Glob, TodoWrite, WebFetch, WebSearch, Task, NotebookEdit, etc.).
      62| 5. **Environment context** — current directory, OS, platform, git status awareness, etc.
      63| 6. **Session resume / compaction summaries** — when resuming or after auto-compaction, a summary replaces earlier turns.

      98| ### 2.2 Permission system
      99| 
     100| This is Claude Code's most distinctive design surface.
     101| 
     102| **Permission modes** (selectable via `Shift+Tab` cycling or `/permissions`; persisted per project/user):
     103| - **default** — safe reads auto-approved; mutating tools (Write, Edit, Bash side-effects) prompt.
     104| - **acceptEdits** — auto-approve file edits; other prompts remain.
     105| - **plan** (plan mode) — read-only exploration; model plans, user approves before execution. Changelog: "plan-mode-for-complex-tasks" tip (verified in local `tipsHistory`).
     106| - **bypassPermissions** (a.k.a. `--dangerously-skip-permissions`) — skip prompts; local config has `defaultMode: bypassPermissions`.
     107| - **auto mode** (newer) — an LLM classifier auto-approves/denies prompts; changelog 2.1.141: "Auto mode permission dialog now explains when a `permissions.ask` rule caused the prompt"; 2.1.147: auto-mode classifier sees user answers as intent signal.
     108| - **sandbox** mode — Bash sandboxing (below) can be combined with modes.
     109| 
     110| **Allow/deny/ask rules** — rule-based lists evaluated per tool invocation:
     111| - Syntax: `Tool`, `Tool(specifier)`, e.g. `Bash(git push*)`, `Edit(src/**)`, `WebFetch(domain:example.com)`, `PowerShell(git push*)` (changelog 2.1.147: hook `if` conditions like `PowerShell(git push*)` now match).
     112| - Three rule tiers: **allow**, **ask**, **deny**. Precedence: deny > ask > allow (roughly; deny wins).
     113| - Stored at multiple scopes: user (`~/.claude/settings.json`), project (`.claude/settings.json`), local project (`.claude/settings.local.json`), enterprise/managed settings (changelog: `forceLoginOrgUUID` / `forceLoginMethod` managed-settings; enterprise login restrictions).
     114| - **"Yes, and don't ask again"** writes a persistent rule (changelog 2.1.147: Windows PowerShell script rule fix).
     115| - Security hardening: changelog 2.1.145: "Fixed a permission-prompt bypass where bare variable assignments to non-allowlisted environment variables in Bash commands were auto-approved" — shows prompt-injection-aware rule matching.
     116| 
     117| **Sandboxing**:
     118| - Bash sandbox released 2.0.24 for Linux & macOS (bubblewrap/Firejail-style network+FS isolation); `/sandbox` menu (changelog 2.1.147: layout fixes to `/sandbox` menu). Windows sandboxing arrived later via different mechanics (version-dependent).
     119| - Sandboxing is orthogonal to permission modes: sandbox constrains what Bash can touch even when auto-approved.
     120| 
     121| **Hooks for permission prompts**:
     122| - Hooks (see §5.1) can intercept **PreToolUse** (can deny/modify before execution), **PostToolUse**, **PermissionRequest** (hook-driven permission prompts), **Stop**, **SubagentStop**, **SessionStart**, **UserPromptSubmit**, etc.
     123| - Changelog 2.1.145: "Stop and SubagentStop hook input now includes `background_tasks` and `session_crons` fields" — hook inputs are JSON-rich and evolving.
     124| - Hook `if` conditions (e.g. `PowerShell(git push*)`) filter when hooks fire (2.1.147).
     125| - Prompt- and agent-type hooks allowed on most events, but `SessionStart`/`Setup`/`SubagentStart` require command-type hooks (2.1.142-era fix).
     126| 
     127| **Trust dialog**: per-project trust on first run (verified locally: `hasTrustDialogAccepted: true` in `.claude.json` for `D:/Tools/AmiClaw`) — gates loading project-level settings/hooks.
     128| 
     129| **File-history / checkpoints**: every file mutation is snapshotted under `~/.claude/file-history/` (verified: 11 session dirs locally). Rewind capability: changelog 2.1.141 "Rewind menu: added 'Summarize up to here' to compress earlier context while keeping recent turns intact" — rewind both code state and conversation.

     133| ## 3. Context Management
     134| 
     135| ### 3.1 Context window limits
     136| - Standard Claude models: **200K token** context window (Sonnet/Opus); **1M context** variants for Sonnet (and merged Opus 1M per local `opus1mMergeNoticeSeenCount`) — changelog `1M` mentions span `2.0.58`→`2.1.144`, with `sonnet1m45MigrationComplete` in local config.

     140| ### 3.2 Auto-compaction
     141| - Introduced early: changelog `0.2.47` — "**Automatic conversation compaction for infinite conversation length** (toggle with /config)".
     142| - When context nears the limit, Claude Code summarizes the earlier conversation into a compact summary, keeping recent turns verbatim. Multiple compaction passes possible for very long sessions.
     143| - Improvements across versions: 2.1.0 "Improved compaction reliability"; 2.1.142-era: "the first summarize attempt now seeds from the original request's overflow size, avoiding a wasted near-full-context retry" (avoids retrying at near-full context).
     144| - **Manual compaction**: `/compact` (with optional focus instruction).
     145| - **Rewind + summarize**: "Summarize up to here" (2.1.141) — compress earlier context while keeping recent turns, i.e. on-demand partial compaction tied to the rewind menu.
     146| - **Micro-compaction**: older tool results are pruned/summarized before full compaction (version-dependent, from public docs **[memory]**).
     147| - `context: fork` in skills: a skill can fork its own context to avoid polluting the main context (2.1.147 infinite-loop fix confirms the feature).

     178| 
     179| ### 4.1 Task tool (subagents)
     180| - **`Task`** spawns a sub-agent with its **own context window** and its own tool loop; the parent receives a single summary result. This isolates noisy exploration (e.g. "search this 50k-line codebase") from the main context.
     181| - Default subagent types: **Explore** (read-only, cheap/fast model, for searching), **Plan** (planning), and general-purpose.
     182| - **`CLAUDE_CODE_SUBAGENT_MODEL`** env var sets the model for subagents (changelog 2.1.147: now applies to teammate processes spawned by agent teams).
     183| - Subagent completion notifications include elapsed duration (2.1.144: "Agent completed — 3h 2m 5s").
     184| - **Background subagents**: subagents can run in the background (pinned via `Ctrl+T` in `claude agents`, 2.1.147: pinned sessions stay alive when idle, restarted in place for updates, shed only under memory pressure).
     185| - **SubagentStop hook** fires on subagent completion (input includes `background_tasks` and `session_crons`, 2.1.145).
     186| - **OTEL tracing**: `claude_code.tool` spans carry `agent_id` / `parent_agent_id`; background subagent spans nest under the dispatching Agent tool span (2.1.145) — observability is first-class.
     187| 
     188| ### 4.2 Custom subagent definitions
     189| - Defined as **Markdown files with YAML frontmatter**: `~/.claude/agents/*.md` (user) or `.claude/agents/*.md` (project).
     190| - Frontmatter fields: `name`, `description` (when-to-use, model-driven selection), `tools` (allowlist), `model` (haiku/sonnet/opus/inherit), plus the markdown body = the subagent's system prompt.
     191| - Plugins can ship agents (changelog 2.1.147: "plugin agents that declare multiple `Agent(...)` types in `tools:` frontmatter" — confirms `tools:` frontmatter syntax).
     192| - Invoked explicitly ("Use the test-runner agent...") or **automatically** when the model delegates matching work; `@agent-name` mentions also work.
     193| 
     194| ### 4.3 Agent teams (multi-agent collaboration)
     195| - **Introduced `2.1.32`**: "Added research preview agent teams feature for multi-agent collaboration (token-intensive feature, requires setting `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`)".
     196| - A **team lead** spawns **teammates** (each a full Claude Code session, run in tmux panes on Unix); teammates communicate via message passing, share a task list, and report back to the lead.
     197| - Evolved through 2.1.x: tmux message send/receive (2.1.33), plan availability fixes (2.1.33), Bedrock/Vertex/Foundry provider env propagation (2.1.45), memory-leak fix for completed teammate tasks (2.1.50), permission-mode inheritance with `--dangerously-skip-permissions` (2.1.98), permission-dialog crash fix (2.1.114), non-ASCII teammate name fix (2.1.145).
     198| - `CLAUDE_CODE_SUBAGENT_MODEL` now applies to teammates (2.1.147).
     199| - This is the most experimental surface: token-intensive, tmux-dependent, Windows support maturing (2.1.144 "macOS background sessions crashing... exit 1 before init when the project..." — platform-specific session management).
     200| 
     201| ### 4.4 Parallelism model
     202| - **Intra-session**: the agent loop is sequential; parallelism comes from (a) background Bash jobs, (b) subagents/teams running concurrently, (c) user running multiple `claude` instances (multi-window / `claude agents` background sessions).
     203| - **`claude agents`**: a session manager/agent view — lists live sessions (`claude agents --json`, 2.1.145), background sessions (`claude --bg`, `/bg`, `/background`), tab titles show awaiting-input count, cross-project resume hints.
     204| - **Background sessions**: `claude --bg` starts detached sessions; `/resume` lists them (marked `bg`, 2.1.144); background-job worktrees (git worktrees per job, Windows NTFS-junction-safe, 2.1.147).

     208| ## 5. Extensibility
     209| 
     210| Claude Code has a deep extensibility stack. From lightest to heaviest:
     211| 
     212| ### 5.1 Hooks
     213| **Hooks** are user-defined shell commands (or prompt/agent-type handlers) that run at lifecycle points, with JSON input/output. They are the primary mechanism for custom permission logic, automation, and guardrails.
     214| 
     215| - **Event points** (from public docs + changelog corroboration):
     216|   - `PreToolUse` — can **deny** or **modify** a tool invocation before it runs (return `{decision: "block"}` or edit the input).
     217|   - `PostToolUse` — react to results (e.g. auto-format after Edit).
     218|   - `PermissionRequest` — custom permission prompts; hooks can auto-approve/deny (this is how teams implement policy beyond the rule lists).
     219|   - `UserPromptSubmit` — validate/transform incoming prompts.
     220|   - `Stop` / `SubagentStop` — on turn/subagent completion (input includes `background_tasks`, `session_crons` since 2.1.145).
     221|   - `SessionStart` / `Setup` / `SubagentStart` — must be **command-type** hooks (2.1.142 fix).
     222|   - `Notification` — on desktop notifications.
     223| - **Configuration**: `hooks` key in settings (user/project/local) or plugin-provided. Hook `if` conditions (e.g. `PowerShell(git push*)`) filter when they fire (2.1.147).
     224| - **Output contract**: JSON with `decision`, `reason`, `updatedInput`, and (since 2.1.141) `terminalSequence` for emitting notifications/window titles/bells without a controlling terminal.
     225| - **Official `hookify` plugin** (in marketplace): "Easily create hooks to prevent unwanted behaviors by analyzing conversation patterns."
     226| - Hooks are **cross-platform** (run via the configured shell; Windows via PowerShell/win_helper, verified locally).

     229| - **First-class integration** (changelog: MCP mentioned in 106 versions, back to `0.2.36`).

     231| - **Scopes**: local (project), project (committed `.mcp.json`), user, enterprise. `.mcp.json` enables team-shared server configs.

     233| - **Tool naming**: `mcp__<server>__<tool>`; servers expose **tools, resources, prompts, and templates** (changelog 2.1.147: "Fixed paginating MCP servers dropping resources, templates, and prompts past page 1").
     234| - **MCP prompts** surface as slash commands (2.1.145: "MCP prompt slash commands showing raw server validation errors... the error now names the missing argument").

     355| ## 8. Known Strengths and Weaknesses
     356| 
     357| ### 8.1 Strengths
     358| 1. **Best-in-class tool harness**: precise file tools (Read/Write/Edit/Grep/Glob) beat generic "run code" approaches for correctness; Edit's exact-match semantics reduce corruption.
     359| 2. **Permission system is the differentiator**: modes + allow/ask/deny rules + sandbox + hooks give a graduated trust model unmatched by most CLI agents. Prompt-injection-aware (env-var assignment bypass fixed, external CLAUDE.md include approval).
     360| 3. **Context engineering maturity**: auto-compaction since v0.2.47, rewind + "summarize up to here", micro-compaction, 1M context variants, CLAUDE.md hierarchy with @-imports and security gating.
     361| 4. **Deep extensibility ladder**: hooks → slash commands → skills → subagents → output styles → plugins/marketplaces → MCP → SDK. The official marketplace (203 plugins, verified) shows ecosystem scale.
     362| 5. **Session persistence & resume**: `--continue`/`--resume`, background sessions, `claude agents` multi-session manager, per-project history — agentic workflows survive restarts.
     363| 6. **Provider flexibility**: Anthropic API + Bedrock/Vertex/Foundry + any Anthropic-compatible endpoint (Ollama etc.) via env vars — no vendor lock-in at the transport layer.
     364| 7. **Headless-first design**: `-p` print mode, stream-json I/O, effort/model flags make it a programmable engine, not just a REPL.
     365| 8. **Observability**: OTEL spans with agent parenting, statusline JSON, usage tracking — enterprise-ready instrumentation.
     366| 
     367| ### 8.2 Weaknesses / user complaints
     368| 1. **Token cost & context burn**: subagents/agent teams are "token-intensive" (2.1.32 changelog's own words); compaction quality is imperfect; long sessions degrade. Agent teams remain research-preview.
     369| 2. **Version churn**: 294 releases to 2.1.148 (verified changelog) — fast-moving target; changelog is dominated by fixes (rendering glitches, Windows Terminal issues, edge-case regressions like 2.1.147's exit-code-127 regression). Feature behavior shifts frequently (e.g. `/simplify` → `/code-review` rename, "extra usage" → "usage credits").
     370| 3. **Platform gaps on Windows**: sandboxing arrived on Linux/macOS first (2.0.24); many changelog entries are Windows-specific rendering/PowerShell fixes — Windows is supported but second-tier.
     371| 4. **Terminal rendering fragility**: recurring fixes for garbled output, resize events, CJK wide characters, VS Code split panes, GNOME paste (2.1.144–2.1.147) — TTY rendering is a moving target.
     372| 5. **Prompt-injection surface**: WebFetch/WebSearch + auto-approval modes + hooks create attack surface; mitigations (permission rules, trust dialog, include approval) exist but users report injection incidents **[community reports, memory]**.
     373| 6. **Permission complexity**: the rule grammar (Tool(specifier), three tiers, four scopes) is powerful but confusing; enterprise admins report configuration sprawl **[community reports, memory]**.
     374| 7. **Anthropic-model coupling**: while endpoints are swappable, behavior is tuned for Claude models; third-party models (e.g. local Ollama, per this machine's config) degrade tool-use reliability, compaction, and classifier quality **[inferred; consistent with local setup using gemma4/qwen3.6]**.
     375| 8. **Opaque internals**: system prompt is not inspectable; compaction/summarization is a black box — hard to debug context failures.
     376| 9. **Experimental surfaces**: agent teams (tmux-dependent, env-flag gated), effort levels, auto-mode classifier — all in flux; APIs/behaviors change between minor versions.
     377| 10. **Security of hooks/plugins**: hooks run arbitrary shell with full user privileges; marketplace plugins are third-party code — supply-chain risk despite `claude plugin validate`.
     378| 
     379| ### 8.3 Implications for AmiClaw comparison (short)
     380| - **Match**: tool inventory, permission rules, CLAUDE.md-style memory, subagents, hooks, MCP client, headless mode.
     381| - **Differentiators Claude Code has**: plugin/marketplace ecosystem, agent teams, checkpoint/rewind, OTEL, managed enterprise settings, output styles, skills.
     382| - **AmiClaw angles to check**: local-model quality under the same harness (Claude Code proves the harness works with Anthropic-compatible endpoints), permission granularity vs. complexity, session persistence model, Windows support parity.
